# Tutorial

A tutorial is a lesson. The reader is new, and you are responsible for their success. They learn by doing one thing that works, not by reading about it.

## Shape

```markdown
# <Build or do a concrete thing>

<One sentence: what the reader will have at the end.>

## Before you begin
- <Exact prerequisites: versions, accounts, installed tools.>

## <Step as an action>
<Instruction.>
<Command or code.>
<What the reader sees now: output, screenshot, or state.>

## <Next step>
...

## Next steps
- <One to three links: the how-to guides or explanations to read next.>
```

## Rules

- Follow one path that always works. Offer no options, alternatives, or "you could also".
- Make every step produce a visible result, and show it, so the reader knows it worked.
- Keep explanation to a clause: "We use a virtual environment so the packages stay isolated." Link to an explanation for more.
- Use "we" for steps you take together ("Now we add a route"). Use "you" for what the reader sees.
- Name the end result in the title and first line. Do not write "In this tutorial, you will learn".
- Test every command in order from a clean start. If you cannot run it, say which steps are untested.

## Leave out

Option lists, configuration reference, design rationale, and troubleshooting beyond the one failure a newcomer is likely to hit.
